## Carrying is not offering

`OnSelectTools` names, per run, the subset of the agent's described tools the run is offered.
Before each run the selector — the host's judgment: a rule, a keyword table, an embedding
index, a cheap classifier — receives the task and the described names, and both offering
surfaces render only what it returned: the `{{tools}}` text catalog and the native tool list
alike. A greeting is offered nothing, and it answers as a greeting should. The Brain still
decides among what was offered; selection shapes the offering, never the decision.

## Narrower offering, unmoved perimeter

An unselected tool behaves exactly like an undescribed one: reachable if the Brain names it,
governed by the same permission, approval and run-once rules, never offered — pinned by a
sabotage that wrote the exact future regression (a loop refusing unoffered acts) and watched
the test catch it. An empty selection validly offers nothing. Names the agent does not carry
are ignored, and the decision log records the truth of the offering — the built-in remember
tool included, so a selector that withholds it is withholding memory writes knowingly. Caller
tools are never selected away: they are the caller's own vocabulary (§4.13). And the offering
is identical on all three doors of the loop, held by a new LoopParity scenario.

## The shapes the tiers demanded

The selector rides `ToolSelector`, a delegate-carrying model — the tier-discipline test
rejected a naked delegate in the service constructor, exactly as it was built to, and the
`ExternalToolCatalog` precedent supplied the correction. The offering rides
`AgentRun.OfferedTools`, ambient per run, for the same reason the run's prompt does: two tiers
below the loop read it, and neither should gain a parameter for it.
